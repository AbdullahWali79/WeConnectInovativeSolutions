## Social Media Campaigns — list loading was slow

- Symptom: `/admin/social-media-campaigns` showed the stat cards filled in but the list stuck on "Loading campaigns…" (worst right after changing a campaign's teacher and clicking "All campaigns").
- Measured Supabase directly (warm): nested campaigns select ~200ms, teachers ~185ms, 30 days ~197ms. **DB was never the bottleneck** — only 1 campaign / 30 days. Cost was in the request chain.
- Root causes:
  1. `page.tsx` only rendered a client component; the list was fetched *after* hydration by two separate server actions (`fetchCampaigns` + `listCampaignTeachers`) → 2× auth (`auth.getUser` ~250–450ms + profile ~200ms) on top of the page's own auth.
  2. `load()` always did `setLoading(true)` → the whole list was replaced by a spinner even when rows were already in state.
  3. `revalidateCampaign` revalidated `/admin/social-media-campaigns/[id]` and `/student/campaigns/[id]` — **neither route exists** (the board is client state on the list route), so that was dead work on every save.
- Fix:
  - New `lib/social-campaigns-data.ts` (`loadCampaignWorkspace`) — plain query helpers, deliberately NOT in a `"use server"` module so the page can call them after it already authenticated.
  - `page.tsx` loads the workspace during the server render and passes `initialCampaigns` / `initialTeachers` / `initialError` down → list paints with the HTML.
  - New `fetchCampaignWorkspace()` action: campaigns + teachers in one authenticated call (replaces the two-action pair).
  - `campaigns-manager.tsx`: `loading` starts false; a `refreshing` flag drives a thin "Updating…" state on the Refresh button; `onBack` / create / new-teacher all refresh silently so rows never disappear.
  - `revalidateCampaign` now only hits the two real routes.
- `npx tsc --noEmit` clean; dev server compiled the route and served warm in ~380ms. Pushed as `a05beea1`.
