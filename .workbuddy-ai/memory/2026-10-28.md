## Accounts Manager: fixed slow loading (payload + refresh strategy)

**Files:** `app/admin/accounts-manager/actions.ts`, `components/admin/accounts-manager/accounts-manager.tsx`

### Root cause (measured against the live DB, read-only via PostgREST)
- `am_clients` holds **3,463 rows**, and `fetchAccountsData()` did `select("*")` on it → **321 KB** on every call.
- That same function ran on **every** mutation (add client, add seller, delete account, remove assignment…), and `loadData()` did `setLoading(true)` first — so the whole list was replaced by "Loading accounts..." each time. That is the spinner the user saw.
- Total initial payload was ~322 KB across 6 parallel queries (accounts 4.7 KB, subscriptions 1.1 KB, followups ~0, sellers/banks ~0).

### Changes
**actions.ts**
- Split into `fetchAccountsWorkspace()` (accounts + sellers + banks + subscriptions + followups, **no clients**) and `fetchClients()`.
- `CLIENT_LIST_COLUMNS = "id, name, phone, whatsapp, marketing_opt_in"` — verified those are the only client fields the picker/renewal UI reads (picker filters on name/phone; renewal uses whatsapp + marketing_opt_in). 321 KB → **144 KB**.
- New `getClientById(id)` for full records when editing.
- `addClient` / `updateClient` now `.select(CLIENT_LIST_COLUMNS).single()` and return `{ client }` so the UI can patch state without a refetch.
- `fetchAccountsData()` kept as a thin wrapper (workspace + clients) for compatibility; no other module imported it.

**accounts-manager.tsx**
- `loadWorkspace({ silent })` replaces `loadData()`: silent refreshes set a `refreshing` flag instead of `loading`, so the list stays on screen.
- Every mutation now calls `loadWorkspace({ silent: true })`.
- **Clients are lazy-loaded**: removed from the initial load. `ensureClientsLoaded()` (useCallback, guarded by `clientsLoaded`/`clientsLoading`) fires when opening the account modal (`openAccountModal()`) or switching to the Renewals tab. Renewals tab shows "Loading renewals…" until ready.
- `upsertClientRow()` patches the local client list after add/edit — but **only when `clientsLoaded`** is already true, otherwise a partial list would be mistaken for the full book.
- `editClientById()` loads the full client via `getClientById` before opening the editor (the list only carries display columns).
- CSV import now refreshes clients only (`loadClients()`).
- Added a subtle "Updating…" indicator (spinner) for background refreshes.
- `AccountFormModal` gained an optional `clientsLoading` prop to show "Loading clients…" in the picker.

### Result
- Initial load payload: **~322 KB → ~6 KB** (clients deferred, loaded on demand at 144 KB).
- After any save: **no full reload, no spinner** — data updates in place.

### Verification
- `tsc --noEmit` clean; `eslint` clean on both files (had to move the `ensureClientsLoaded` useCallback above the effect that uses it — `const` doesn't hoist like `function` declarations).
- Dev server: `✓ Compiled /admin/accounts-manager`, GET 200, warm requests 0.7s. Could not test the data path end-to-end — needs an authenticated admin session.

**Environment note (recurring):** `next dev` / `next build` intermittently die with `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` when cleaning `.next`. Workaround that works: run `rm -rf .next` as its **own** command, then start the server as a separate background command.

## Accounts Manager: new client missing from the "Link Clients" picker

**Files:** `app/admin/accounts-manager/actions.ts`, `components/admin/accounts-manager/accounts-manager.tsx`

### Root cause — PostgREST's silent 1,000-row cap
`fetchClients()` did `.select(...).order("name")` with **no pagination**. PostgREST caps every response at the project's `db-max-rows` (1,000 on Supabase) and truncates *silently*.

Proven against the live DB:
```
curl -I ".../rest/v1/am_clients?select=id" -H "Prefer: count=exact" -H "Range: 0-0"
→ Content-Range: 0-999/3463
```
The 1,000th name alphabetically is **"C S Aurangzaib PPIT BSSE 3rd Semester"** — so every client sorting after it (~2,463 of 3,463, i.e. **71% of the book**) was invisible in the picker. Any newly added client whose name sorts past that point could never appear. This was NOT a race with `ensureClientsLoaded()` as first suspected.

The same cap silently broke `importClients()` dedupe: it read only the first 1,000 `name, phone` pairs, so CSV re-imports duplicated everyone beyond that.

### Changes
**actions.ts**
- `PAGE_SIZE = 1000` + `selectAllPages(page)` helper that loops `.range(from, to)` until a short page comes back.
- `fetchClients()` now paginates (verified: 1000+1000+1000+463 = 3463) and adds `.order("name").order("id")` — a stable secondary sort so range pagination can't skip/repeat rows.
- New `searchClients(term, limit = 25)`: server-side `or=(name.ilike.*q*,phone.ilike.*q*,whatsapp.ilike.*q*,email.ilike.*q*)`, capped at 50. Strips `% , ( ) *` from the term because they're structural in PostgREST filters. Verified against the live API.
- `importClients()` dedupe read now paginated.

**accounts-manager.tsx**
- `AccountFormModal` no longer takes `clients` / `clientsLoading`. The picker **searches the server** (debounced 220 ms) instead of filtering a local array, so it sees all 3,463 clients and the modal no longer has to wait for a book load.
- `openAccountModal()` no longer preloads the client book → opening "Add Account" is faster (no 144 KB fetch).
- Added `InlineClientEditor` (rendered inside `AccountFormModal`): create a client **or** edit full details without leaving the modal. It is deliberately **not** a `<form>` (it lives inside `#account-form`; nested forms are invalid HTML) — submits via `onKeyDown` Enter + explicit buttons.
- New client is **auto-linked** to the account on save (`handleClientSaved`), so no extra click.
- Each search result has a pencil button → `getClientById` → same inline editor.
- Empty state offers `Add "<query>"` pre-filled with whatever was typed.
- `upsertClientRow` unchanged (still gated on `clientsLoaded`) — only the standalone `AddClientModal` uses it now.

### Verification
- `tsc --noEmit` clean; `eslint` clean on both files; dev server `GET /admin/accounts-manager` → 200.
- Could not click through the modal — the route redirects to login without an admin session.
- DB behaviour verified directly via PostgREST (pagination + `or=` filter syntax).

## New module: Social Media Campaigns (client day-wise posting plans)

**Why:** client work is managed in a hand-kept Excel sheet (`Adam_Azam_30_Day_Social_Media_Growth_Plan.xlsx`): Week 1–4 × Mon–Sun, columns Day | Video Link | Script & Caption | Status. A teacher and students produce posts daily; the teacher picks the best; admin verifies. Goal: replace the sheet with a live board.

### Reference workbook structure (from sheet-agent inspection)
6 sheets. The core one is **`30-Day Calendar`**: header row 1, **30 data rows**, **19 columns** — Day, Date, Theme, Goal, Research/verify, Facebook plan, Instagram plan, X plan, Caption, Image headline, X post draft, Official source/link, Reel script, Hashtags, Engagement action, CTA, Metrics to record, Status, Published URL. Gotchas: `Date` is plain text ("Oct 29", no year); F/G/H are byte-identical in all 30 rows; `Source/link` is not always a URL; `Reel script` is the only multi-line column; `Published URL` is 100% empty. Other sheets: Daily Workflow (8 steps), Weekly Metrics (5 weeks × 3 platforms), Growth Tracker, Platform Guide, Read Me (Period + Goal).

### Files added
- `supabase/migrations/20261028000000_social_media_campaigns.sql` — `sm_campaigns`, `sm_campaign_days`, `sm_campaign_members` + RLS (admin all / teacher own / student member) + indexes + `set_sm_campaigns_updated_at` trigger.
- `lib/social-campaign-plan.ts` — workbook → day rows. Matches columns **by header text, not position**; infers the year from Read Me `Period` and rolls it forward on month wrap; collapses the triplicated FB/IG/X column into one `platform_plan`; reads the Read Me title for the client name.
- `app/admin/social-media-campaigns/actions.ts` — CRUD, bulk day import, dual approval, member assignment. Uses the service client, so teacher scoping is enforced in code via `assertCampaignAccess`.
- `components/admin/social-media-campaigns/campaigns-manager.tsx` — list, create modal with plan upload + preview, teacher creation.
- `components/admin/social-media-campaigns/campaign-board.tsx` — day grid, expandable detail, per-day teacher/admin approval toggles, team + Drive links panel.
- `app/admin/social-media-campaigns/page.tsx`

### Design decisions
- **Dual approval is two independent columns** (`teacher_status`, `admin_status`), not one chain — either approver marks a day Done, matching the stated rule. Derived display state: published > done > missed (past date, not done) > pending.
- **Drive links are admin-assigned per user**: `sm_campaigns.drive_folder_url` (shared with students), `sm_campaigns.teacher_drive_url`, `sm_campaign_members.drive_url` per student. No upload integration in this phase.
- Teacher scoping via `sm_campaigns.teacher_id`; a teacher owns many campaigns, a student joins many via `sm_campaign_members`.
- New permission group `social_campaigns.{view,create,edit,delete,approve}` in `lib/admin-permissions.ts`; nav item added to the Communication group.
